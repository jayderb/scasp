# SCASP Architecture

## Problem definition
The institution needs one controlled platform where students can access academic services and staff can manage academic operations. The prototype centralises course information, registration, waiting lists, service requests, announcements, reporting and campus-service locations.

## Intended users
- Students: browse courses, register/withdraw, join waiting lists, submit service requests, read announcements and locate campus services.
- Academic staff: manage courses, process requests, publish announcements and view reports.
- Administrators: manage accounts/roles, review audit records and monitor platform health.

## Functional requirements
1. The system shall authenticate demo student and staff users.
2. The system shall enforce role-based access to staff functions.
3. Staff shall create, update, search and deactivate courses.
4. Students shall view the course catalogue.
5. Students shall register for an active course.
6. The system shall prevent duplicate active registrations.
7. The system shall reject registrations when the student is unknown.
8. The system shall enforce course capacity.
9. The system shall add eligible students to a FIFO waiting list when a course is full.
10. Students shall withdraw from a course.
11. The system shall promote the next waiting student after a place becomes available.
12. Students shall submit academic service requests.
13. Staff shall prioritise, assign and update service requests.
14. Staff shall publish announcements to selected audiences.
15. The system shall record important actions in an audit trail.
16. Staff shall view registration, waiting-list and request-workload reports.
17. Students shall view configured campus-service locations.
18. The system shall provide a TCP gateway for selected commands.
19. Administrators shall retrieve reports through an RMI client.
20. The system shall provide a web interface and Android client.

## Non-functional requirements
1. Security: validate inputs and enforce roles.
2. Reliability: handle errors and unavailable services safely.
3. Performance: use bounded worker resources for concurrent processing.
4. Scalability: separate modules and allow additional workers.
5. Maintainability: use cohesive classes and service interfaces.
6. Portability: avoid machine-specific file paths.
7. Usability: provide clear navigation and error messages.
8. Data integrity: enforce keys, constraints and transactions.
9. Availability: use timeouts and orderly shutdown.
10. Auditability: record actor, action, entity and timestamp.

## Context diagram (text form)
External actors: Student, Staff, Administrator.
SCASP exchanges login details, course requests, registrations, service requests and announcements with students; course updates, request decisions and reports with staff; and account/audit/reporting information with administrators. SCASP stores records in a relational database and exposes controlled network, web, RMI and Android interfaces.

## Component architecture
Android/Web/Desktop clients -> HTTP/Servlet or RMI/TCP gateways -> application services -> domain model/repositories -> JDBC database. Concurrent processing workers handle background request and notification tasks. Audit events are generated by service operations.

## Key domain invariants
- A student may have only one active registration per course.
- Active registrations must never exceed course capacity.
- A student cannot register for an unknown or inactive course.
- A student cannot appear twice on the same waiting list.
- Promotion is FIFO unless an explicitly documented priority rule is adopted.
- Only authorised staff/admin users can perform staff operations.
- A closed service request cannot be reopened through an ordinary status update.
- Every important state change creates an audit event.

## Risk register
| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Integration delays | Medium | High | Integrate small increments and use stable interfaces |
| Different development environments | Medium | Medium | Document JDK, Maven and server versions |
| Legacy CORBA tooling unavailable | High | Medium | Submit IDL and migration dossier; use ORB only if provided |
| Team availability | Medium | High | Assign owners and maintain a contribution log |
| Data inconsistency | Medium | High | Database constraints and transactions |
| Concurrent registration race | Medium | High | Synchronise service operations and test invariants |
| Security misconfiguration | Medium | High | Validate input, check roles, avoid committing secrets |
| Android network failure | Medium | Medium | Handle offline states and provide controlled mock data |
